ReplayFoundry Grounded Editorial CUDA Memory Policy 1.1

Purpose

This policy keeps grounded Qwen editorial metadata from consuming the full
local CUDA device through PyTorch's native caching allocator and removes the
qualified vision encoder from the constrained CUDA allocation. It changes no
model weight, precision, prompt, video sampling, decoding, grounding, or
semantic validation rule.

Fixed configuration

- Scope: grounded editorial metadata only.
- CUDA device: 0.
- Allocator: PyTorch native CUDA caching allocator.
- Reserved allocator headroom: 3,221,225,472 bytes (3 GiB).
- Allocator limit: reported free device memory at admission minus the fixed
  headroom, expressed to PyTorch as a fraction of total device memory.
- Startup free-memory gate: the computed allocator limit must remain greater
  than the retained qualification peak before model loading begins.
- Pre-generation gate: after releasing only unoccupied PyTorch cache blocks,
  current reported free device memory must remain at least the fixed 3 GiB
  headroom before each grounded model generation begins.
- KV cache implementation: Transformers offloaded DynamicCache.
- Model precision: every floating-point model parameter remains BF16.
- Language-model placement: CUDA device 0.
- Vision-encoder placement: CPU, through one explicit Accelerate device map.
- Other CPU model offload: prohibited.
- Disk model offload: prohibited.
- Quantization: prohibited.
- Automatic cap relaxation or fallback: prohibited.

Placement rationale

The pinned Qwen model contains 830,695,424 bytes of BF16 vision parameters.
Keeping that branch and its transient vision activations outside the fixed
CUDA allocator directly reduces the failed visual-generation peak. The text
language model remains on CUDA. The host validates every parameter and buffer
against this exact split after loading and fails before inference if the
loader changes it.

Qualification reference

The retained `real-qwen-metadata-v1.6.json` artifact uses schema
`replayfoundry-editorial-metadata-real-quality-1.0`, has SHA-256
`0EC7F4BE4DD3664091D6808176B2FEA36B7FE016B277422DACA00C4C9D28EC70`, and
measured 11,705,485,312 peak PyTorch-allocated GPU bytes under the older,
more demanding all-CUDA placement. That peak remains the conservative
minimum allocator admission threshold; this policy does not use the CPU
placement as permission to shrink or relax the established CUDA cap.

Limitations

The fixed headroom is a limit on allocations managed by PyTorch's CUDA caching
allocator. It does not include every CUDA-driver, library, Windows WDDM, or
other-process allocation and therefore does not guarantee that 3 GiB remains
globally free. The startup and pre-generation gates are contention guards, not
reservations from other processes. If a fixed allocator or admission gate
cannot be met, the command fails closed; it does not weaken the policy,
quantize the model, or move additional language-model modules to CPU.

Audit

Every grounded metadata execution records the policy version and hash, cache
implementation, reported total, startup-free, and externally occupied device
bytes, required startup-free bytes, fixed allocator headroom, computed
allocator limit, minimum viable limit, configured and observed allocator
fractions, the retained qualification peak, pre-generation admission count
and minimum/current free-memory observations, peak allocated and reserved
bytes, end allocated/reserved/free bytes, runtime outcome and failure reason,
and explicit policy flags for the required vision-only CPU placement,
quantization, global-free-memory guarantee, and fallback.
